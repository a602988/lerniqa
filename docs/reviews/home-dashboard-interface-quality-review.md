## 發現

### IQ-01 [高｜信心高｜usability] 沒有考試次別資料，介面卻把它呈現為有效篩選

- 位置：首頁「安排練習」的「考試範圍」；`app/page.tsx:261-267`、`app/page.tsx:645-651`
- 使用者任務或契約：家長選定一次定期評量的範圍後，孩子應取得該範圍對應的題目。
- 證據：在正式預覽分別選取「第二次定期評量」與「第三次定期評量」，本次題數都維持 5，開始後第一題都為「一個平角是多少度？」。程式的 `filtered` 只依年級與科目篩選，沒有讀取 `exam`。
- 問題：介面將考試範圍呈現為會影響練習的輸入，但它目前只改變右側摘要文字。
- 後果：家長會誤以為題目已符合考試範圍；孩子可能練到不相關內容，且使用者無法從結果判斷設定其實未生效。
- 建議：現有題目只有科目與單元，不能任意補上考試次別。移除不可履行的次別控制，改由既有的科目與單元產生真正可執行的「練習範圍」；正式 ExamPlan 與定期評量範圍仍留在下一階段。不可把任意分配的示範資料假裝成真實考試範圍。
- 共用邊界：篩選條件與摘要應由同一份可執行的練習設定模型擁有，避免表單顯示值與題目查詢各自演進。
- 驗證方式：切換科目與現有單元後，題數、摘要及實際練習佇列必須共同改變；沒有題目的組合顯示誠實空狀態。畫面不得再聲稱能依考試次別篩選。
- 版本影響：patch
- 調整結果：把次別降為不影響題目查詢的「評量名稱」，並明確以題庫既有科目與單元建立同一份篩選、題數、摘要及 session 佇列；無題目組合會顯示空狀態並停用開始動作。
- 狀態：已驗證

### IQ-02 [高｜信心高｜usability] 錯題答對後在顯示回饋前消失

- 位置：錯題複習流程；`app/page.tsx:268-280`、`app/page.tsx:380-396`、`app/page.tsx:677-692`
- 使用者任務或契約：學生重做錯題後應先看到答對／答錯、解析與下一步，再由系統更新待複習清單。
- 證據：先將第一題答錯，確認錯誤回饋與解析可見；回到「錯題」後答對同一題，畫面立即變成「目前沒有待複習的錯題」，沒有顯示「答對」回饋。程式以每題最新紀錄即時計算 `mistakes`，而目前錯題畫面又直接使用這個可變清單。
- 問題：提交正確答案的同一次狀態更新會先把目前題目移出 `activeQuestions`，使作答回饋流程失去題目。
- 後果：學生無法確認自己是否真的答對，也看不到成功回饋或解析；最後一題尤其像是內容突然消失。
- 建議：開始錯題複習時固定本次題目佇列，提交後保留目前題目和回饋，待使用者按「下一題／完成複習」後才從下次清單移除。
- 共用邊界：一般練習與錯題複習應共用穩定的 session／question-flow 狀態契約；歷史統計更新不應直接改寫進行中的題目佇列。
- 驗證方式：建立一筆錯題，進入複習後答對；必須先看到正確回饋，按下一步後才出現下一題或完成狀態，重新進入錯題時該題已移除。
- 版本影響：patch
- 調整結果：一般練習與錯題複習都在開始時固定題目佇列。Chrome 實測錯題答對後，題目、正確狀態、解析與「完成複習」仍保留；完成後再從待複習清單移除。
- 狀態：已驗證

### IQ-03 [中｜信心高｜usability] 完成整份練習沒有結果，且「本次」統計其實是歷史最新紀錄

- 位置：一般練習最後一題與首頁統計；`app/page.tsx:268-275`、`app/page.tsx:400-416`、`app/page.tsx:613-627`、`app/page.tsx:758-773`
- 使用者任務或契約：學生完成一輪題目後，應知道本輪完成、答對數、錯題與可採取的下一步；標示「本次」的數字應屬於當前練習。
- 證據：在正式預覽完成 5 題並按「完成練習」，畫面直接回到安排頁，沒有完成訊息或結果摘要。首頁顯示 5/5，但程式是從該學習者對目前題庫的歷史最新答題紀錄計算，不是本輪 session。
- 問題：最後一步只呼叫 `returnToPlan()`；介面把累積狀態標成「本次」，且沒有一個可供孩子或家長理解本輪成果的結束狀態。
- 後果：完成感、學習回饋和下一步不明確；重複練習時數字可能看似已完成，造成錯誤期待。
- 建議：增加精簡的完成狀態，清楚區分本輪答題結果與累積進度；提供回到安排、複習本輪錯題等符合現有功能的下一步，不擴增新的學習功能。
- 共用邊界：題目佇列、本輪作答與累積紀錄應各有明確所有權，所有「本次」標籤、進度條和結果頁使用同一 session 資料。
- 驗證方式：從乾淨紀錄完成一輪、再完成第二輪；每輪結果各自正確，回到首頁的累積數字與標籤不會冒充本輪結果。
- 版本影響：patch
- 調整結果：新增本輪結果頁，明列題數、答對及待複習，並提供複習本輪錯題與返回安排；首頁數字改為累積語意。本輪 3 題、答對 2 題、待複習 1 題已在 Chrome 驗證。
- 狀態：已驗證

### IQ-04 [中｜信心高｜visual] 次要文字與未選取導覽的對比不足

- 位置：品牌副標、說明文字、未選取導覽、摘要標籤與頁尾；Keel `--color-muted-foreground`
- 使用者任務或契約：小字說明和未選取但仍可操作的導覽必須在白色與米色背景上保持可讀、可辨識。
- 證據：正式預覽計算樣式為 `#9ba6b7`；與白色背景的對比約 2.46:1，與右欄 `#fbf3e8` 的對比約 2.24:1。代表文字多為 12–14 px，低於一般文字 4.5:1 的基準。
- 問題：低對比色同時承擔裝飾性附註與重要操作／狀態文字，視覺安靜但可讀性不足。
- 後果：低視力、低品質螢幕或戶外使用者更難讀取；未選取導覽看起來近似停用。
- 建議：提高語意上的次要前景色，使一般字級達到至少 4.5:1；若仍需要更淡的裝飾色，另設只用於非必要圖形的 token，不要套在可操作標籤。
- 共用邊界：由全站 semantic token 統一處理並抽查 Button、FormField、CardDescription、摘要及 footer，避免逐處硬編顏色。
- 驗證方式：量測所有代表性背景上的正常字級對比；Chrome 高對比／灰階檢視仍能分辨可操作導覽與停用狀態。
- 版本影響：patch
- 調整結果：完成後的紫色主題把次要文字設為 `#696b82`，對白色約 5.22:1；主要藍紫、紫、莓紅、金棕與主按鈕色的白字對比分別約 5.16:1、5.66:1、4.98:1、5.20:1 與 5.00:1。頁首標誌紫色 `#745ee8` 對白色約 4.66:1；代表性正常字級皆超過 4.5:1。
- 狀態：已驗證

### IQ-05 [中｜信心高｜component] 主要導覽沒有可感知的目前狀態與可見鍵盤焦點

- 位置：左欄／手機頂部「練習、錯題、匯入」導覽；`app/page.tsx:563-588`
- 使用者任務或契約：鍵盤與輔助科技使用者必須知道目前位於哪個區域，也必須看見焦點移到哪個控制項。
- 證據：三個按鈕只以 `appearance` 與 `tone` 改變外觀，沒有 `aria-current`、`aria-pressed` 或 tab 語意。以 Tab 聚焦時 DOM 符合 `:focus-visible`，但實際計算樣式為 `outline: none`、`box-shadow: none`，畫面沒有可辨識焦點。
- 問題：視覺選取狀態沒有暴露成可感知語意，且 Keel 按鈕在目前主題組合下沒有落地成可見焦點。
- 後果：鍵盤使用者容易失去位置；螢幕閱讀器無法得知目前工作區，增加誤操作與返回成本。
- 建議：依導覽語意採 `aria-current`（或使用具完整鍵盤契約的 Keel Tabs／同等元件），並在實際主題上提供不只依賴色彩、清楚且不被裁切的 focus-visible 樣式。
- 共用邊界：焦點樣式應在 Keel Button／主題封裝層修正，並同步抽查主要、次要、ghost、outline 與導覽按鈕；目前狀態則由導覽元件負責。
- 驗證方式：只用鍵盤依序操作三個區域；每一步焦點清楚可見，輔助科技能宣告目前區域，滑鼠點擊後也不產生錯誤狀態。
- 版本影響：patch
- 調整結果：目前導覽加入單一 `aria-current="page"` 與非純色彩視覺狀態；主要控制、題目／結果標題與對話框控制都有可見 `focus-visible`，下一題與返回安排會把焦點送到新內容標題。
- 狀態：已驗證

### IQ-06 [中｜信心高｜component] 設定對話框關閉後沒有把焦點還給開啟按鈕

- 位置：學習者設定；`app/page.tsx:471-527`、`app/page.tsx:590-597`
- 使用者任務或契約：從「學習者設定」開啟模態視窗，關閉後應回到原觸發控制，讓鍵盤使用者接續操作。
- 證據：開啟時初始焦點正確落在稱呼欄位；按 Escape 可關閉，但關閉後 `document.activeElement` 是 `BODY`，不是「學習者設定」。程式使用受控 `Dialog`，外部 Button 沒有與 Keel `DialogTrigger` 建立觸發關係。
- 問題：模態視窗能關閉，但缺少可靠的焦點還原目標。
- 後果：鍵盤使用者回到頁面後失去位置，通常必須從頁首重新 Tab。
- 建議：優先使用 Keel `DialogTrigger asChild` 建立正式觸發關係；若受控情境確實需要外部控制，則以 trigger ref 和 close-auto-focus 契約顯式還原。
- 共用邊界：所有 Dialog 呼叫端應沿用同一開啟／關閉／焦點還原模式，不在單一頁面臨時補 DOM focus。
- 驗證方式：分別以 Escape、關閉圖示與「完成」關閉；三種路徑都回到觸發按鈕，Tab 順序接續且不落到背景隱藏內容。
- 版本影響：patch
- 調整結果：改用 `DialogTrigger`／`DialogClose` 契約；Escape、關閉圖示與「完成」三種路徑都已驗證會回到「學習者設定」按鈕。
- 狀態：已驗證

### IQ-07 [中｜信心高｜combined] 手機採 compact 密度，核心開始動作被前置資訊推到第二屏

- 位置：320–390 px 的首頁安排流程；`app/layout.tsx:21-27`、`app/page.tsx:528-672`、`app/page.tsx:737-779`
- 使用者任務或契約：孩子或家長在手機上應能舒適觸控主要控制，並快速找到「開始練習」。
- 證據：全站固定 `data-density="compact"`。390 px 寬時導覽、選單與設定按鈕多為 32 px 高，主要按鈕 36 px，單選題標籤可點區約 20 px；「開始練習」頂端約在頁面 y=1105（844 px 視窗之外）。320×720 時約在 y=1161。各測試寬度沒有水平溢位，但學習者卡、三個導覽、歡迎標頭、三格統計後才到表單，右欄又重複部分摘要。
- 問題：桌機資訊架構直接垂直堆疊到手機，觸控密度偏小且最重要的任務入口被框架資訊與重複統計壓後。
- 後果：小孩較容易誤觸；首次使用者需要長距離捲動才能開始核心任務，產品看起來完整但操作效率不像成熟行動產品。
- 建議：手機改用舒適密度和約 44 px 的主要觸控目標；保留品牌與必要的學習者識別，但折疊／精簡側欄式導覽與重複摘要，讓安排表單及開始動作在第一屏或一次短捲動內出現。桌機三欄方向可保留。
- 共用邊界：尺寸由 Keel density／Button／Input／Radio 的響應式契約統一處理；頁面只負責手機資訊排序，不逐個控制硬編高度。
- 驗證方式：在 320、390、768 px 及實體觸控裝置回歸；主要控制達到一致可觸範圍，無水平溢位，200% 文字縮放仍可操作，開始練習不被固定／折疊內容遮擋。
- 版本影響：patch
- 調整結果：採舒適密度、重排手機資訊與一致 44 px 控制；320、390、768、1920 px 實測皆無水平溢位，390 px 的開始按鈕位於一次短捲動內，1920 px 內容寬度封頂 1440 px。
- 狀態：已驗證

### IQ-08 [中｜信心高｜visual] 通用畢業帽無法形成可辨識的 Lerniqa 品牌資產

- 位置：首頁品牌列、瀏覽器分頁圖示與 Apple touch icon；`app/components/lerniqa-mark.tsx`、`public/lerniqa-mark.svg`、`public/favicon.ico`、`public/apple-icon.png`
- 使用者任務或契約：品牌標誌應在頁首與 16–44 px 小尺寸維持一致、清楚且不依賴通用圖示庫辨識。
- 證據：修改前品牌列直接使用 Lucide `GraduationCap`，且專案沒有 favicon、Apple touch icon 或專屬品牌資產；此符號常見於大量教育產品，不能承擔品牌識別。
- 問題：通用線性畢業帽既缺少獨特性，小尺寸也依賴細線；頁首與瀏覽器分頁沒有一致的識別來源。
- 後果：即使整體配色成熟，產品仍容易被看成套版或原型，且跨入口的品牌記憶不連續。
- 建議：保留既有名稱與最終紫、粉紅、深墨色方向，建立單一原創向量標誌，再由相同幾何輸出頁首、SVG favicon、32 px ICO 與 180 px Apple icon；不可宣稱已完成商標或全球相似圖形查重。
- 共用邊界：品牌元件只負責標誌幾何；功能圖示仍使用既有 Lucide／Keel 圖示，不把品牌符號誤用成操作圖示。
- 驗證方式：檢查 16、32、44、180 px 輸出、透明背景、Chrome 頁首與 favicon metadata、桌機／手機品牌列以及原畢業帽是否完全移除。
- 版本影響：patch
- 調整結果：建立「Lerniqa Learning Card」原創圖形——圓角學習卡、上方提把與紫／粉節點構成的練習軌道。頁首元件、SVG、32 px ICO 與 180 px Apple icon 已統一成同一幾何與紫色品牌方向，16／32 px 預覽仍可辨識。此為原創構圖提案，不代表商標可註冊性或排他性結論。
- 狀態：已驗證

## 第二輪完成後複檢

本節針對開發者完成五個工作區與新版紫色視覺後的實際頁面。問題是在該完成訊號後才確認，未覆寫開發中途狀態。

### IQ-09 [高｜信心高｜usability] 篩選後題數與可選上限不一致

- 證據：完成版先產生固定 3／5 題選項，再縮小科目與單元；英文示範題實際只有 1 題，但控制仍可能承諾更多題數。
- 後果：設定摘要與真正 session 佇列不一致，使用者無法預期本輪長度。
- 調整結果：`eligibleQuestions` 成為單一來源；題數選項、摘要與 session 都由同一集合產生，年級變更也會重設已失效範圍。Chrome 實測選英文後只出現「1 題」，開始後確實只有 1 題。
- 狀態：已驗證

### IQ-10 [高｜信心高｜usability] 進行中的練習可能被靜默丟棄，計時與學習者歸屬也不可靠

- 證據：切換工作區、學習者或年級可直接清除作答中狀態；作答紀錄缺少 session 擁有者與每題開始時間，秒數及資料歸屬可能與實際操作不符。
- 後果：孩子的輸入可能無提示消失，家長切換學習者後也可能把結果記到錯誤對象。
- 調整結果：session 加入 `learnerId`、`questionStartedAt`，每題以實際時間計算；已有答案、手寫或已完成題目時，離開／切換會出現確認，當前工作區按鈕則不清除 session。Chrome 已驗證取消離開後答案仍保留。
- 狀態：已驗證

### IQ-11 [高｜信心高｜accessibility] 純手寫題無鍵盤等價操作，且尚未檢視會被當成答錯

- 證據：純手寫書寫題原本無法只靠鍵盤提交；資料模型只有布林正誤，未經 OCR 或人工判讀的手寫內容沒有誠實狀態。
- 後果：鍵盤或輔助科技使用者被阻擋，且系統會捏造錯誤判定、污染錯題與正確率。
- 調整結果：手寫板新增可存計算／書寫內容的鍵盤筆記，disabled、label、狀態訊息與替代文字完整；純手寫以 `correct: null` 儲存並顯示「待檢視」，不計入已檢核正確率，也不再列入錯題。Chrome 以只填鍵盤筆記完成國字題，結果正確顯示「待檢視」。
- 狀態：已驗證

### IQ-12 [中｜信心高｜content] 示範功能與數字曾被描述成已完成服務

- 證據：題目匯入按鈕、相近題佇列、版本篩選、成果檢視及部分進度／時長文案，曾超出目前本機示範資料真正能完成的能力。
- 後果：家長可能誤以為檔案已上傳、OCR／AI 已處理、版本已篩選或檢視決策已儲存，形成產品承諾風險。
- 調整結果：匯入改為「完成校正示範」並明示不會上傳／辨識；版本標示為偏好資料；相近題只有存在固定示範題時可加入並可真正啟動；日期、時長、進度與統計改由實際紀錄計算；未保存的成果選項改稱「檢視設定（示範）」。
- 狀態：已驗證

### IQ-13 [中｜信心高｜accessibility] 內容切換焦點與平板觸控尺寸不完整

- 證據：下一題／結果後焦點可能留在已消失控制，手機捲動位置會延續；768 px 版部分控制仍只有 36 px，練習方式也缺少 fieldset／legend 群組。
- 後果：鍵盤、螢幕閱讀器與觸控使用者較難理解頁面已切換，平板誤觸風險高。
- 調整結果：工作區、題目及結果標題成為程式化焦點目標；模式使用 fieldset／legend，進度有可讀名稱，768 px 以下至 1023 px 的可見 button／select／input／textarea 最小高度為 44 px。最終 build 實測 390 與 768 px 無水平溢位，且可見控制最小高度皆為 44 px。
- 狀態：已驗證

### IQ-14 [中｜信心高｜state] 舊資料與損毀本機資料缺少安全遷移

- 證據：新版狀態曾只做淺層讀取；無效 v3 資料可能被預設值立即覆寫，舊版 v1 作答也沒有遷移路徑。
- 後果：升版後可能靜默遺失家長與孩子在同一瀏覽器的示範紀錄。
- 調整結果：加入欄位、型別、長度、日期與有限數值驗證；有效 v1 作答會依學習者與題目遷移，成功寫入 v3 後才移除舊 key；遇到無效 v3 時阻止自動覆寫並顯示錯誤。
- 狀態：靜態與型別驗證通過；仍缺自動化 migration 測試

### IQ-15 [中｜信心高｜visual] 頁首與安裝圖示輸出品牌不一致

- 證據：完成版頁首已改成紫色 Learning Card，但 `public/lerniqa-mark.svg` 仍是前一版紫色 Practice Loop，`favicon.ico` 與 `apple-icon.png` 更仍是綠色環形標誌。
- 後果：同一產品在頁首、瀏覽器分頁與加入主畫面時呈現三種圖形，明顯像未收尾的原型。
- 調整結果：以頁首元件為準統一 SVG、ICO、Apple PNG 與 16／32 px 審查預覽；小尺寸點陣與 180 px 輸出已目視檢查。
- 狀態：已驗證
