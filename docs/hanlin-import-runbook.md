# 題庫匯入與排錯

這份文件保存已驗證的匯入故障、修正方式與重跑順序。它只適用於 repository 內的本機 PostgreSQL，以及目前列入白名單的國文、數學題庫來源，不是 production 操作手冊。來源文件留在本機，不要把真實學生資料、密碼、token 或本機完整路徑寫進紀錄。

## 每次正式匯入前後怎麼做

### 來源欄位的保存、tag 與篩選契約

來源文件每題若提供「認知向度」或「知識向度」，匯入器必須把兩者分開保存，不得遺漏、互相覆蓋或只留在匯入預覽／`import_items.draft_payload`。非空值必須同時寫入目前題目 revision 的 `question_revision_filter_values`，保留來源文件的原始標籤與原始值，並透過題庫 API 回傳，讓題目詳情顯示 tag、題目總覽與練習設定產生可用篩選選項。沒有該欄位的題目不得捏造預設值。

新增其他來源欄位時也遵守同一契約：先定義穩定的欄位 key、名稱、值型別與適用範圍，再保存每題的來源值並完成 API、tag、篩選與回歸測試。畫面出現文字不代表資料已可篩選；驗收必須同時確認 current revision 的欄位值、API metadata、題目 tag 與實際篩選結果。parser 若改變來源欄位內容，必須升版並建立新 revision，舊 revision 保留為 `superseded`，不得就地修改已發布版本。

### 題目文字、數學符號與圖片契約

- 來源中的 `×`、`÷`、`＝`、`＋`、`－`、括號、上下標、不等號與箭頭都屬於題目內容，匯入後必須保持語意與順序。不得把空白一律取代成 `×`：日期、帶分數、座標、單位與一般文字也可能合法包含空白。
- 題幹或解析若出現疑似因 Word 轉換而遺失乘號的算式，例如 `a＝2 3 5`，匯入器必須加入 `suspected-missing-multiplication-sign` 並保持待檢視。只有逐題對照核准原檔後，才可加入固定題號、固定內容的窄範圍修正；不得依公式外觀猜測後整批替換。
- 若檢核命中的是合法空白、題號或排版，而非遺失乘號，仍須逐題對照核准原檔，並以固定題號加入 `APPROVED_MISSING_MULTIPLICATION_FALSE_POSITIVES`。不得放寬全域規則；來源中確有公式殘缺、頁碼殘留、解析截斷或其他問題的題目必須繼續待檢視。
- 已發布題目的文字或符號修正必須建立新 revision，舊 revision 保留為 `superseded`。修正時一併核對題幹、選項、答案與解析，避免只修畫面中的其中一處。
- 可由原檔明確還原的上下分數，以 `\frac{分子}{分母}` 寫入題幹、選項、答案或解析；共用題目文字元件會顯示成上下排列的分數。只有來源公式內容已逐項確認時才可轉換，普通的 `3/4`、日期與比例文字維持原樣，不得依斜線自動猜成分數。
- 圖片是題目內容區塊，不是附註文字。題幹圖放在題幹內，選項圖綁定對應選項／小題，答案圖與解析圖分別放在答案或解析區；同一位置有多張圖時必須保留原始順序。
- `alt_text` 只供無障礙與圖片載入失敗時使用，不得投影成可見題目文字或搜尋本文。因此「2-1 因數與倍數 題目附圖」這類替代文字不應顯示在題幹，也不得重複寫進題目內容。
- 圖片映射必須至少固定原檔 SHA-256、題號、圖片 checksum 與 placement；選項圖另須固定 option key，小題圖另須固定 part key。圖片缺漏、破損、順序不明、位置無法判定，或只剩 OCR 文字而無法還原原圖時，一律保持待檢視，不得發布誤導內容。
- 圖片應直接從核准 Word 原檔抽取，不得以畫面截圖、人工重畫或來源不明的相似圖替代。匯入驗收至少抽查純文字題、含題幹圖、含選項圖與含數學公式題，並在桌面與手機寬度確認圖片位於正確內容區且不溢出。

### Word 原生覆核與巨集規則

- 待檢題先由同一份固定 SHA-256 的核准 Word 快照產生 PDF 與 HTML：PDF 用於固定頁碼與目視版面，HTML 用於取得文字、公式與資產順序，DOCX／Word 仍是內嵌物件與圖片 bytes 的權威來源。只有 PDF、HTML 與靜態 Word 內容互相一致時，才可用 PDF 加速逐頁覆核；任一來源不一致、版面截斷、圖片位置不明或公式無法唯一判讀時，必須回到 Microsoft Word 以唯讀方式檢查，不得以 PDF 或 OCR 猜測缺失內容。
- Word 原生覆核必須記錄原檔 SHA-256、來源相對路徑、題號、頁碼，以及圖片在題幹、解析、小題或 A–D 選項中的實際位置。若 Word 中可見完整圖片，必須從原始 Word 資產取得 checksum 並建立一對一映射；畫面截圖只能作為覆核證據，不能代替正式匯入圖片。
- Word 原生覆核預設以唯讀方式開啟，巨集、ActiveX 與「啟用內容」一律保持停用。即使檔名與 SHA-256 都在白名單內，也不得由匯入流程或自動化操作執行 VBA；白名單只能證明來源身分，不能證明巨集行為安全。若靜態開啟後仍無法完整呈現題幹、公式、圖片、選項或解析，該題保持待檢視並記錄阻擋原因，不得以啟用巨集換取發布資格。覆核期間不得編輯、儲存或覆寫原檔。
- 正式匯入程序一律維持隔離 profile、停用巨集與 ActiveX，且只接受以固定 SHA-256、題號、圖片 checksum、placement、option key 或 part key 核准的靜態結果。人工在 Word 中啟用內容不代表匯入器可以執行巨集，也不代表該題可以省略圖片映射證據直接發布。
- 公式圖片答案原則上維持待檢；只有固定來源 SHA-256、唯一題號、唯一來源頁、完整原始欄位 preimage 與公式圖片 checksum 全部相符，且 PDF、HTML、Word 靜態內容可一對一證明文字公式時，才可由來源限定的修正 registry 還原文字答案。修正必須自然通過原有守門規則並建立單題新 revision，不得直接刪除 pending reason，也不得覆寫修訂開始後出現的較新 current revision。

### 翰林英文圖片與逐題稽核規則

- 翰林英文舊版 Word 可能先出現題幹與圖片，之後才出現該題的題號與分類欄位。圖片必須依文件結構綁定實際題號，不得因「目前尚未讀到下一題題號」而掛到前一題；重新匯入前後都要逐題比較 placement、option key、part key 與圖片 checksum。
- 多小題看圖作答題若同時包含共用參考圖與各小題圖片，匯入映射必須為每張小題圖片固定 `partStableKey`，writer 以 `question_part_id` 和小題內 position 保存；共用圖才可維持 root block。同一題若重複使用相同 checksum，映射必須另存以 1 起算的 `sourceOccurrence`。序號的範圍固定為正規化題號與 checksum，且同組序號必須完整、不重複並連續為 `1..N`。匯入器依 Word 來源中的圖片出現順序選擇 mapping，不依 registry 陣列順序選擇。只有固定來源 SHA-256、題號、圖片 checksum、來源出現序號、完整且不重複的小題 key 全部相符時，才可移除主題幹末尾重複的編號標記。缺少、超出、未知、重複、序號不連續或 checksum 不符時必須拒絕匯入，不得依圖片數量或陣列順序猜測。單一 checksum 的既有 mapping 可以省略 `sourceOccurrence`。
- Word 中的破圖圖示、`Image...`、空白圖片框或其他只用來表示遺失資產的站位內容，不是題目圖片，不得建立 image block，也不得把站位文字寫入題幹。若原生 Word 可看到真實圖片，但無法從核准原檔讀出完整 bytes、checksum 或唯一位置，該題必須保持待檢視／停用，不得以缺圖狀態發布；不得用截圖或相似圖片替代。
- LibreOffice 的 HTML 圖片衍生檔不得單獨作為圖片完整性的證據。若可視內容從畫布四分之一之後才開始，且貼齊右緣或下緣，視為疑似保留物件位移後遭裁切；稽核必須報錯。只有固定原檔 SHA-256、原始 EMF checksum、題號與 placement 的一對一契約，才可從原始 EMF 靜態轉成 PNG；轉換僅可裁除外圍近白畫布，不得人工補畫內容。

### 翰林英文克漏字底線與空清單規則

- 舊版 Word 以底線格式標示的 `　(1)　`、`　(2)　` 等克漏字位置，匯入後必須保留編號與可取得的兩側空格；共用題目文字元件將整段呈現為帶編號的底線。若行尾空白在文字正規化時被移除，只要編號前仍有來源全形空白，行尾 `(1)` 仍視為同一個作答底線。不得刪除編號，也不得把沒有來源空白的一般內文 `(1)` 自動視為作答空格。
- 舊版 Word 可能用 EQ overstrike 欄位保存講者名稱，例如 `eq \\o\\ar(　　　,George):`。LibreOffice 安全轉檔若只留下行首冒號，parser 必須從相同 SHA-256 的已核准來源快照讀取靜態文字，且只在唯一題號、對話行順序與冒號後全文完全相符時補回講者；只容許轉檔已知會移除的行尾留白差異，內文空白也不得任意折疊。來源題號重複或任一行無法一對一核對時，必須停止該次匯入，不得刪除冒號、猜測講者或發布缺名對話。
- Word 來源可能在題幹前保留編號或項目清單節點；LibreOffice／純文字轉換可能把它輸出成英文題幹開頭的 `•`、`●`、`▪` 或 `◦`，標記可能獨立成行，也可能和正文同行。parser 只可移除英文題幹最前方的單一清單標記與其相連空白；正文中間或後續行的項目符號不得全域刪除。
- 修改上述規則後必須盤點所有 current 英文題目：帶編號克漏字須顯示底線，題幹不得以上述清單標記開頭，普通小題編號與正文內的項目符號必須維持原樣。parser 版本必須升級並為內容有變的正式題目建立新 revision，舊 revision 保留為 `superseded`。

## 已驗證的故障與修正

### 匯入批次狀態的 PostgreSQL 參數型別衝突

- 現象：第一次正式寫入在完成批次狀態時失敗，PostgreSQL 回報 SQLSTATE `42P08` 的參數型別推斷衝突。
- 已驗證根因：同一個 `$2` 同時寫入 `varchar(20)` 欄位，又在 `CASE` 中與字串常值比較。PostgreSQL 對兩個使用位置推斷出不相容的型別。
- 修正位置：`scripts/lib/hanlin-postgres-writer.mjs`。`SET status` 與 `CASE WHEN` 都明確使用 `$2::varchar(20)`。
- 驗證結果：加上 cast 後，parser v1 的 279 題正式寫入成功。`tests/hanlin-import-guardrails.test.mjs` 會防止兩個 cast 被移除。
- 預防檢查：正式匯入使用 `npm run db:import:hanlin -- ...`，讓 `test:import-preflight` 先執行；修改狀態 SQL 後再跑一次實際交易驗證。
- 適用版本：所有使用目前 PostgreSQL writer 的匯入；parser v1 發現，parser v2 仍保留修正。

### 選擇題答案鍵不屬於該小題的選項

- 現象：資料模型原本可能保存畫面上不存在的答案鍵，造成學生無法選到標準答案，判分也會失真。
- 已驗證根因：`question_answers.answer_key` 與 `question_options.option_key` 跨資料表，原本的欄位限制不能保證兩者屬於同一個 `question_part_id`。
- 修正位置：`database/migrations/0007_practice_answer_integrity.up.sql` 加入可延後的 constraint trigger；`scripts/lib/hanlin-postgres-writer.mjs` 也在發布前確認單選答案存在於同一小題的選項。
- 驗證結果：`database/tests/0007_practice_answer_integrity.sql` 已覆蓋不存在的答案鍵、刪除或改名仍被引用的選項，以及把答案或選項移到另一小題的情況；合法的同交易改名仍可通過。
- 預防檢查：修改題目、選項、答案 schema 或 writer 後執行 `npm run db:test`；不要在正式環境停用或繞過延後限制。
- 適用版本：schema `0007` 之後。

### 盤點目錄被誤當成第四課正式匯入範圍

- 現象：15 份來源文件曾一起 dry-run 盤點，容易被誤解為都可以歸入第四課。這次沒有把其他 14 份文件寫入資料庫，也沒有產生錯誤分類的正式題目。
- 已驗證根因：檔案可被解析，只代表格式可讀；它不代表產品已核准年級、冊別與課次分類。目錄盤點和正式寫入是兩種不同權限的操作。
- 修正位置：`scripts/import-hanlin-chinese-postgres.mjs` 只允許正式寫入白名單中的第四至第六課與語文常識（二）來源；每份來源都要求固定檔名、原檔 SHA-256、目標單元與預期狀態。匯入器會用單一檔案描述元讀入來源，先把這組 bytes 寫進私有暫存快照，後續轉檔與隔離備份都只使用這份快照，避免驗雜湊後的來源替換競態。目錄、其他檔名，或同名但內容不同的檔案都不可正式寫入。
- 驗證結果：第四至第六課的 parser v5 confirmed 批次各只含一個來源文件，題數為 279、280、258；語文常識（二）的 parser v6 review 批次解析 76 題、發布 75 題，兩張有效統計圖以固定 checksum 對應題號 `05011868`、`05011869`，來源已破圖的 `05011838` 保留待檢視。2026-10-17 再從固定來源還原並發布三題：`05013285` 的四個統計圖選項與答案 B、`05013836` 的四列文字選項與答案 D、`05013843` 的四張對話圖選項與答案 B；圖片選項各自連到 A–D，不得合併成題幹附圖。目前資料庫共有 1,095 個國語 current published revision，1 個來源題號待檢視。前置測試會確認非授權檔名在讀檔前就被拒絕，也會拒絕改成授權檔名的其他內容。
- 預防檢查：每一個新課次都要先有自己的核准分類、固定檔名與預期題數，才能擴充正式寫入白名單；不可只改命令列路徑。
- 適用版本：目前核准第四至第六課與語文常識（二）的本機持久資料匯入。

### parser 升級後的分類候選識別衝突

- 現象：parser v2 第一次正式寫入失敗，錯誤為 `DATABASE_IDENTITY_CONFLICT`，欄位是 `source_document_classification_candidates.parser_version`。
- 已驗證根因：v1 的分類候選固定識別沒有包含 parser 版本。v2 重用相同 ID 時，writer 發現同一筆 ID 的 `parser_version` 不同，因此拒絕覆寫歷史。
- 修正位置：`scripts/lib/hanlin-postgres-writer.mjs`。原始 unit 候選與七個正式分類候選的 deterministic ID 都包含 `plan.parserVersion`；每個分類維度只保留目前版本的一筆 `approved`，舊版本改為 `rejected`，原始待核對候選仍保留。
- 驗證結果：v2 批次 `2d1ff794-f6f4-5e59-baaa-8d1c767438be` 成功解析並發布 279 題、失敗 0 筆、重新分類 279 題。相同輸入再跑時 `reusedBatch=true`、重新分類 0 題，仍是 279 題。v1 的七筆正式分類已改為 `rejected`，v2 七個維度各只有一筆 `approved`，違反唯一正式分類的查詢為 0 筆。
- 預防檢查：任何會改變解析或分類結果的 parser 升級都要改版本；固定識別中必須保留 parser 版本，並測一次舊版資料升級與新版相同輸入重跑。
- 適用版本：parser v2 之後。

### 舊版 Word 的 `\S\do` 序號控制碼進入題幹

- 現象：parser v1 寫入後，279 個 current revision、282 個 current content block 含有 `\S\do` 前綴，正常練習畫面會直接顯示 Word 版面控制字串。
- 已驗證根因：LibreOffice 轉換舊版 `.doc` 時，把部分 Word sequence field 保存成可見文字；這些字串是題號版面指令，不是題目內容。
- 修正位置：`scripts/lib/hanlin-chinese-import.mjs` 的 `stripLegacyWordSequenceFieldPrefixes`，在解析題目之前移除已知前綴。它只處理行首的既知結構，不會刪除一般數字開頭，例如「2026 年」。
- 驗證結果：parser v2 寫回後，資料庫 279 題的 current revision 全部是 revision 2；current content 中含 `\S\do` 的題目與內容區塊都是 0。單元測試覆蓋兩種實際控制碼與一般數字開頭。
- 預防檢查：新增 Word 來源格式時先 dry-run，抽查題幹並搜尋 `\S\do`；若出現不同控制碼，只新增能重現該格式的窄規則，不用廣泛刪除反斜線或數字。
- 適用版本：parser `hanlin-zh-doc-v2`。

### 失敗交易留下半套資料或資產

- 現象：批次狀態型別衝突與第一次 v2 分類候選衝突都發生在正式寫入流程；若資料庫與資產各自提交，失敗可能留下沒有完整題目的批次或沒有資料庫引用的資產。
- 已驗證根因：資料庫交易與本機檔案系統不能共用同一個原子提交，因此 writer 必須在資料庫提交前驗證資產，並在資料庫失敗時執行補償回滾。
- 修正位置：`writeHanlinPostgresImport` 從 `BEGIN` 到 `COMMIT` 包住整批資料，錯誤時執行 `ROLLBACK`；資產先進 staging，`beforeCommit` 成功後才提升，提交失敗時移除本次新增的資產。提交結果不明時則保留資產並停止，避免刪掉其實已被提交的資料。
- 驗證結果：兩次已知寫入失敗都完整回滾，沒有留下部分批次或題目；修正後才一次寫入完整 279 題。正式匯入前後的備份另由 `npm run db:local:backup` 驗證 dump 與資產 checksum。
- 預防檢查：不要把單筆 writer 呼叫移出交易，也不要在 `COMMIT` 前直接覆寫正式資產；故意注入錯誤時要比較失敗前後批次、題目與資產筆數。
- 適用版本：目前 PostgreSQL writer 的所有版本。

### 目標分類覆蓋原始課次證據

- 現象：所有核准題目都要進第四課，但來源文件內仍有「今之孝者」「譬如為山」「吾日三省吾身」等原始 unit。若只保存正式 target，之後無法追查來源怎麼分段。
- 已驗證根因：來源解析值與產品核准分類用途不同，不能共用一個欄位互相覆蓋。
- 修正位置：writer 在 draft payload 保存 `originalTitle`、`originalUnit` 與 `originalLabels`；分類候選另存一筆沒有 target ID 的 pending 原始 unit，再把第四課保存成獨立的 approved target。
- 驗證結果：279 題的原始 unit 分布為「今之孝者」67 題、「今之孝者／譬如為山／吾日三省吾身」1 題、「吾日三省吾身」92 題、「譬如為山」110 題、「譬如為山／吾日三省吾身／今之孝者」9 題。`scripts/verify-local-practice.mjs` 會拒絕缺少原始 unit 候選、含私人絕對路徑或缺少第四課正式分類的資料。
- 預防檢查：新增解析欄位時先分清楚它是來源證據還是正式分類；正式分類可以更新，來源檔名、雜湊、原始標籤與解析結果不可被 target 值取代。
- 適用版本：目前所有翰林 Word 匯入。

### build、重啟與 3500 port

- 現象：已有開發伺服器監聽 3500 時再次啟動會回報 `EADDRINUSE`。Next.js 開發程序與 build 同時操作 `.next` 也不能當成可靠驗證。
- 已驗證根因：同一個 port 只能有一個監聽者；更重要的是，dev 與另一個 dev/build 同時共用 `.next` 會改寫瀏覽器正在使用的 chunk。200 回應仍可能伴隨 `ChunkLoadError`，畫面會卡在「正在確認登入狀態」。
- 修正位置：`next.config.ts` 接受 `LERNIQA_NEXT_DIST_DIR`；`npm run dev` 固定使用 `.next-dev`，`npm run build` 與 `npm start` 使用 `.next-build`。不要另開第二個 3500 dev 程序，但分離後的 build 不會再破壞正在服務的 dev chunks。
- 驗證結果：受控重啟後 `http://127.0.0.1:3500/`、`http://127.0.0.1:3500/account` 與 `http://127.0.0.1:3500/local-practice` 都回傳 HTTP 200；瀏覽器還必須完成 hydration，不可只看 HTTP 狀態。
- 預防檢查：每次 build 後都檢查三個入口與瀏覽器 console，不只看終端顯示「ready」。可用 `curl --fail --silent --show-error`；畫面或 API 有改動時仍要做瀏覽器操作驗證。
- 適用版本：目前 Next.js 15 本機流程。

### 康軒數學 Word 上標被拆成多段 `^()`

- 現象：同一個視覺上標可能因 Word 字型或斜體切換，被轉成相鄰的多段標記，例如 `7^(2)^(＋3)`；舊式方程式物件也可能把上標中的乘號拆成 `10^(3)× ^(5)`。此外，作答欄解析器曾把 `2^(4)` 的 `(4)` 誤認成第 4 小題。
- 已驗證根因：Word run 邊界不是數學語意邊界，不能直接把每個 superscript run 當成獨立指數；小題編號也不能匹配前面緊接 `^` 的括號。
- 修正位置：`scripts/lib/hanlin-chinese-import.mjs` 的 parser `kangxuan-math-doc-v4` 合併沒有基線運算元分隔的相鄰上標片段，並保留真正的巢狀次方；`scripts/import-grade-seven-fixtures.mjs` 排除 `^(` 的小題誤判；`app/lib/question-presentation.ts` 與 `app/components/bopomofo-text.tsx` 統一把 `^(...)`、`_(...)` 顯示為上標、下標。
- 全量來源稽核：必須執行 `scripts/audit-kangxuan-math-scripts.mjs`，以固定 SHA 重新解析核准的 11 份來源，逐題保存來源檔名、來源頁、題幹、小題、選項、答案、解析與待檢視原因；不可只搜尋資料庫中的 `^` 字元，也不可自動猜測缺失公式。
- 2026-10-18 驗證結果：11 份來源共 1,020 題，545 題可發布、475 題待檢視；275 題含上標或下標。可發布題目的破損公式語法為 0。僅三題仍有來源轉換缺口，全部維持待檢視且不對學習者發布：`1501005035`（題庫題目／第一冊／2-2，來源第 22 頁，空下標）、`1501004244`（題庫題目／第一冊／2-4，來源第 3 頁，行尾裸 `^`）、`1501000015`（仿會考非選題／第一冊／2-3，來源第 1 頁，空上標及未解析行內公式圖）。
- 顯示驗證：題號 `1501003309` 已在桌面及 390×844 手機寬度實際確認，選項、解答與解析均顯示真正上標，不再把 `^()` 原碼顯示給使用者。
- 預防檢查：任何數學 Word 解析規則變更都要升 parser 版本、跑完整 11 來源稽核、確認 `publishedSyntaxIssueCount=0`，再執行單元測試、型別檢查、production build 與桌面／手機瀏覽器驗證。無法由來源唯一還原的公式一律保留待檢視。
- 適用版本：parser `kangxuan-math-doc-v4` 之後。

### 翰林英文舊版 Word 圖片空白、被裁切或模糊

- 現象：部分英文題目的衍生 GIF 只有空白、圖面向右下偏移並在畫布邊界被裁切，或雖然內容完整但文字明顯模糊；這些都是已保存資產的像素問題，不是前端圓角或 `object-fit` 造成。
- 已驗證根因：LibreOffice 從舊版 Word 產生的 HTML/GIF 沒有完整保留內嵌 EMF 圖面，而且舊 HTML 衍生圖只有約 96 DPI。另有兩個管線問題：核准的 `replacesDerivedChecksum` 曾在 EMF 轉成 PNG 的中間物件遺失；舊 GIF 位於題號之前時，依鄰近題號判斷會失去正確關聯。部分圖片是 OLE 物件的預覽 EMF，不在一般 DrawingML 圖片序列中。
- 修正規則：每張圖必須同時符合固定來源 SHA-256、原始 EMF SHA-256、題號、待替換衍生 GIF checksum 與最終 PNG checksum。一般 DrawingML 圖依圖片名稱及 relationship 配對；OLE 預覽依同一個 `<w:object>` 的 `ObjectN` 順序與 `v:imagedata` relationship 配對。任一來源、順序或 checksum 不符就停止匯入，不以檔名、位置距離或視覺相似度猜測。
- 轉換規則：核准的 EMF 先用隔離的 LibreOffice profile 轉成 PDF，再以 `pdftoppm -png -r 300 -singlefile` 產生 300 DPI PNG，最後只裁除近白外框。在該已核准來源內依精確 checksum 排除舊衍生圖，依契約順序保留多圖；其他同題圖片不可移除。LibreOffice 或 Poppler 版本若造成最終 PNG checksum 改變，必須重新目視稽核並提高 parser 或轉換契約版本，不可直接更新 checksum。任何內容改變都建立新 revision，不修改既有 published revision。

## 仍未定論的觀察

### 社會科舊版 Word 的逐檔待檢修復

- 社會科待檢題必須一次只處理一份來源 Word：先用 Microsoft Word 開啟並停用巨集，保存題幹、答案、解析、表格與圖片存在性的證據，關閉文件後再 dry-run、寫入及回查；不得同時開啟多份來源。
- 自動覆核器開檔前必須確認 Word 沒有任何文件；若 Word 僅停在開始畫面則先退出。完成單一來源後必須以不儲存方式退出 Word，並確認程序已結束，才可開啟下一份。這是避免舊版 `.doc` 圖片載入造成 Word 記憶體不足的必要條件。
- 表格或圖片修復只接受固定原始來源 SHA-256、題號及圖片 checksum 的具名契約。表格欄位可由 Word 文字層逐格重建；圖片選項必須保持來源順序並綁定選項代號。多小題圖片應綁在對應 `partStableKey`，不可集中附在題尾。
- 同一份 Word 可能在多個題號重複使用完全相同的圖片 bytes；checksum registry 必須先保留同 checksum 的全部核准映射，再以題號選出唯一項目，不得用單值 Map 覆蓋其中一題。
- LibreOffice 版本改變若使安全轉檔 bytes 改變，必須提高 sanitizer 版本並使用含版本的 storage key；不得覆寫較早 sanitizer 版本的來源快照。目前社會科使用 `libreoffice-macro-disabled-docx-v2` 與 parser `hanlin-social-v9`。v7 新增經 Microsoft Word PDF 逐格或逐頁字元核對、並以原生表格 checksum 鎖定的 Word 表格結構化匯入；v8 再加入「選項位於原生表格內」的來源 SHA、題號及表格 checksum 限定修復；v9 只在來源區段標為填充題、題幹第一個非空白行明列「是非題」，而且來源答案是可明確換算的 ○／╳、對／錯或是／否時，改以 `boolean` 自動評分並將來源題型標籤保存為「是非題」。缺少任一項證據時仍按原來源題型處理，不由答案符號單獨猜測題型。舊版 revision 與 import evidence 保留不覆寫。
- parser 曾因缺圖把已發布題安全封存時，後續只有固定來源 SHA-256 與逐題核准契約明確標記的題目可以恢復；一般封存題仍不得自動重新發布。最新待檢統計依來源相對檔名與題號跨 parser 版本排序，不能以不同 `source_document_id` 的歷史 pending 重複計數。
- Word 物件若在 Word 文字層、圖片擷取及頁面轉譯都無法唯一還原，該題繼續保持 pending。禁止使用正確答案或解析反推遺失的選項、箭頭圖例或表格內容。
- 每份文件的驗收至少包含 targeted dry-run `pendingReview=0`，或逐題記錄不可恢復的 pending 原因；正式寫入後再查 current review status。全批完成前還要執行匯入守門測試、型別檢查、production build 與資料庫有效最新版本統計。
- 整份來源含封存題時，不得為了更新另一題而解除整份文件的封存狀態。社會科匯入器以 `--source-path`、`--question-number`、`--correction-version` 三個參數共同啟用逐題修訂；只保留該題的唯一可發布 occurrence，使用 parser 版本及 correction version 建立新 revision，並只對這個固定來源 SHA 的逐題修訂允許恢復先前由 parser 撤回的同一題。
- 2026-10-18 原生表格全量結果：62 份含 Word 原生表格的來源文件已逐份由 Microsoft Word 輸出 PDF；222 個原生結構中，164 個為有語意表格、56 個為單欄排版結構、2 個為純圖片排版容器。164 個表格分布於 163 題，全部已由固定來源 SHA、題號、來源頁、表格順序及逐格文字 checksum 驗證並存在於 current published revision；資料庫回查為 164/164 通過，缺漏、列值不符及題幹重複攤平皆為 0。9 題因選項位於表格內而曾被一般選項解析器擋下，已以 v8 逐題修訂恢復，答案與 PDF 相符。

### 社會科共用圖片代號配合題

- 現象：題號 `05010290` 的五個小題以同一張經緯線地圖上的 `A` 至 `F` 作為共同選項；Word 文字層保留小題與答案，但共同選項只存在於圖片，因此一般文字配合題解析會回報 `multi-part-parse-failed`。
- 已驗證根因：舊解析器只從第一小題前的文字尋找共同選項，沒有可追溯的視覺選項證據；不能從答案中出現的最大字母反推圖片一定包含完整選項。
- 修正規則：parser `hanlin-social-v4` 只接受固定來源 SHA-256、題號及題幹圖片 checksum 完全相符的視覺配合題契約。契約明列人工核對的 `A` 至 `F`，再由通用小題解析器驗證五個答案依序為 `B、D、C、F、E`。來源、圖片或答案任一不符時仍維持待檢，不做 OCR 或答案範圍猜測。
- 2026-10-18 驗證結果：該來源 dry-run 為 134/134 可發布、待檢 0；正式寫入後 `05010290` 為 published，包含 5 個獨立單選小題、每題 6 個選項、5 筆答案及 1 張共用題幹圖片。正式寫入前備份位於 `local-data/backups/lerniqa-local-20261018T050128Z`。
- 類型邊界：文字共同選項複選、圖片代號複選及同題混合作答不是本規則的安全延伸；必須先保存每小題答案群與作答模式並另做來源契約，未完成前繼續待檢。
- 回歸檢查：執行 `node --test tests/hanlin-import-guardrails.test.mjs`，並以核准來源做 targeted dry-run；資料庫需確認 5 個 parts、每 part 6 個 options、答案 `B/D/C/F/E`，且共用圖片只出現一次於 prompt。

同一來源在不同 CLI 摘要中曾分別顯示 47、59 與 61 頁。目前沒有足夠證據確認原因，因此不能把任何推測寫成修正，也不能只用頁數判斷匯入成功。若要處理，先保存相同來源 checksum、轉換工具版本與各次可重現輸出，再定位差異；題數、來源範圍、current revision、內容控制碼、分類唯一性與批次重跑仍是現在的驗收條件。

## 新增故障紀錄時要留下什麼

### 數學公式與多欄答案的 Chrome 驗收門檻

- 題幹、作答與解答中的結構化公式共用 KaTeX 公式樣式；除了使用 display style，Chrome 實測公式容器字級不得低於 `1.5rem`，不能只以 KaTeX DOM 已存在判定完成。純文字解析中的 `\\frac` 使用共同行內分數元件，字級不得小於相鄰文字，分數線須和同列等號維持同一視覺中心。
- 含結構化公式的多行題幹使用專用列高。Chrome 實測相鄰兩列公式盒子之間必須有正間距；一般文字題幹不得套用這個列高。
- 來源公式中的 `\\phantom` 是刻意保留的作答空格。匯入、顯示與修正流程都不得把它判定為遺失數字、破圖或可由答案反推的內容。
- 多欄答案列的 `(1)`、`(2)` 等編號必須是畫面上的一般可見文字，字級不得低於 `1.125rem`，不能只放在 `legend`、`aria-label` 或螢幕閱讀器專用內容。
- 固定驗收題 `1501004796` 必須在 Chrome 桌面與 390px 手機寬度顯示四列編號與 `2／3／2／2` 共九個欄位，且公式清楚、欄位不溢位。

只記錄能讓下一個人重現與驗證的內容：錯誤碼或可觀察現象、最小重現命令、來源 checksum 與 parser/schema 版本、已證實的根因、修改檔案、同一重現步驟的修後結果，以及新增的回歸測試。根因還沒證實時直接標為「待調查」，不要把猜測寫成結論；紀錄內不放密碼、token、email、本機完整路徑或真實兒童資料。
