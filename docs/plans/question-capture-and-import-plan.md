## 目前交付範圍

### 2026-10-20 圖片解析與練習式編輯調整

狀態：已完成並通過最終驗收。

- `IQ-QA-01`：圖片題目分析必須把校正圖片與 OCR 行座標一併交給固定本機 vision 模型。圖片是內容依據，OCR 只供定位與比對，不得再因 OCR 字數足夠而省略圖片。
- `IQ-QA-02`：國字注音題必須保留原稿的作答位置。模型不得補出完整詞語、答案或原稿未印出的整詞讀音。模型注音只有在 OCR 候選含完全相同字串時才能直接保存；沒有相同候選時要以緊密 `crop_ref` 留在原位置。模型結果若含替代字元、日文假名、拉丁字母、空白引號、同一括號混合國字與注音，或把注音移到作答位置外，系統須重試一次。第二次仍不可信就保留原稿與既有草稿。
- `IQ-QA-03`：章節序號、題型名稱與計分說明只作為解析線索。其下直接排列的編號項目各自建立為獨立題目，分類標題不得進入題幹；只有不可缺少的共用素材後面有多個相依問題時才建立題組。模型第一次未通過題目格式契約時，第二次重試必須收到具體錯誤，不得原樣重送。
- `IQ-QA-04`：待確認的注音裁切在草稿編輯器中維持原本內容順序。使用者可放大私人裁切圖，並依原稿輸入注音、聲調與可選的成對引號或括號；國字、拉丁字母、日文假名與不成對外框不得確認。確認後只把該裁切替換成輸入文字，其他題幹內容與原始上傳檔保持不變。
- `IQ-AUTHOR-01`：新增題目的主要編輯區改成練習式題目卡。桌面同時顯示原始頁面與可編輯題目，窄螢幕改為上下排列；題幹、小題、作答區、解答與解析、作答前提示依編輯工作順序排列。
- `IQ-AUTHOR-02`：一般單題底部使用「建立題組」；轉成題組後才顯示「新增小題」。新增後立即顯示一張可編輯小題卡；作答方式與答案在同一張卡內設定，低頻的父子題與批改設定放入「更多設定」。
- `IQ-AUTHOR-03`：科目、年級、版本、單元與自訂分類仍只在最後「加入題庫」步驟確認，不混入題目內容編輯。

回退方式：解析調整可回復到本文件前一版的單次 OCR 輸入；介面調整只重排既有草稿欄位，不變更草稿與正式題目資料格式。若實際瀏覽器驗證無法保持既有題型、圖片、表格、提示或答案能力，撤回介面改動，不以刪減功能換取版面簡化。

### 2026-10-21 多份來源與答案建議

- 同一個 `import_batches` 可連結 1 至 20 份來源文件。檔案順序與用途都保存在 `import_batch_documents`，不先合併為 PDF，避免失去每張圖片的用途、來源頁碼與證據關係。
- `document_role` 使用 `auto`、`question`、`answer`、`explanation` 或 `supplement`。使用者沒有指定時，由固定本機 vision model 判斷並保存信心值與理由；使用者明確指定或修改後，以使用者設定為準。
- worker 逐份完成頁面校正、OCR 與去除彩色手寫，只對 `question` 來源建立題目。`answer`、`explanation` 與 `supplement` 來源仍保留處理後頁面，供答案建議及人工比對。
- 題目拆分與答案建議是兩個邊界。拆題階段沒有來源答案時維持空答案與 `manual_review`；後續答案建議可讀取所有來源，優先採用答案頁與解析頁，否則依題目推導並降低信心。建議保存於工作結果，不直接寫入 `import_items`。只有使用者在編輯器確認後，答案與解析才進入草稿。
- 尚未填寫答案的作答區提供「AI 分析答案與解析」。手動觸發時只依目前題目內容推導該小題，產出答案、簡短解析與信心值；這是前景請求，執行中須在按鈕旁顯示處理狀態，完成、資訊不足或失敗訊息也須留在同一位置。結果仍是待確認建議，使用者按下「套用答案與解析」後才寫入編輯內容。已有答案時不得顯示或呼叫此操作，也不得覆寫既有答案與解析。
- 手動解題必須區分注音題的作答方向。題幹以引號或括號包住純注音時，該注音是待填國字的讀音線索；模型須依前後文提出國字，不得重複題幹內已有的注音，也不得把相鄰國字的讀音當成答案。這項解題規則不得改變圖片辨識階段逐字保留原稿、禁止補答案的規則。
- 重新分析前可調整全部來源用途。用途與背景工作同時修改時，後端拒絕更新，避免完成結果使用一半新設定、一半舊設定。
- 已建立的圖片或 PDF 草稿可在「原始檔案」區繼續加入多張圖片或 PDF。新增前先保存目前的來源用途，再把新檔追加到同一個 `import_batches` 並重新分析整份草稿；不得另建草稿或只分析新檔。背景工作執行中暫停新增，完成或失敗後可再加入，總數仍以 20 份為上限。
- 草稿名稱使用獨立完整列；原始檔案、數量、新增入口及檔案卡片依序列在名稱下方。多份檔案使用響應式網格，手機改為單欄，不能讓檔案預覽或新增操作造成水平溢位。
- 每份原始檔案卡片採直向排列。上方只顯示可點擊的圖片縮圖或 PDF 圖示，不顯示額外的查看文字；下方直接使用共用 `AppSelect` 顯示 32 px 高的用途選單。檔名與用途仍保留在預覽對話框及可存取名稱中。
- 新增多檔說明、掃描處理說明與目前草稿狀態合併成一句，直接放在「原始檔案」標題與檔案數量下方。桌面版位於三個新增按鈕左側；手機版依閱讀順序位於按鈕上方，不再另外顯示掃描提示列或草稿狀態。
- 「儲存用途並重新分析」屬於整份草稿的操作，桌面版放在草稿名稱欄位右側並與輸入框底部對齊；680 px 以下改為輸入框下方滿寬按鈕，不再放在原始檔案清單下方。
- 草稿名稱輸入框與右側「儲存用途並重新分析」按鈕在桌面統一為 2.65 rem 高度及相同圓角；680 px 以下兩者改為 2.75 rem，維持滿寬排列與觸控尺寸。
- 建立題目工作台的導覽、頁首、建立方式、編輯、來源與內容工具按鈕使用緊湊尺寸，避免按鈕壓過題目內容。原始檔案區的裝置選檔、拍照及貼上按鈕使用同一寬度與 32 px 高度；`label` 與 `button` 必須套用相同的橫向內容排列，不能受草稿欄位的通用 `label` 樣式影響。680 px 以下仍保留至少 44 px 的主要按鈕點擊高度；原始檔案按鈕維持 32 px，「新增提示」及內容類型工具則使用 28 px 高的最小尺寸。
- 「檔案上傳／格式匯入／手動編輯」建立方式使用同一個滿寬分頁列，三個選項平均分配可用寬度；桌面與手機不得退回只佔左側的獨立膠囊群組。
- 草稿開啟、背景處理與儲存結果等狀態顯示在「建立題目／我的草稿」大標題旁，不另占一整列；窄螢幕可在同一標題列中自然換行。
- 題目卡內不再使用一個外框包住整份編輯內容；題目內容與答案建議使用白底及細邊框。作答前提示區只以分隔線區分段落，每筆提示保留一層邊界。所有文字、公式、表格與圖片內容區塊不另加外框；桌面版把拖移排序、內容與刪除排在同一列，手機版才將內容移到下一列。淡紫色只用於選取狀態、進度及主操作，不再用來填滿多層內框。
- 學習者作答區的最外層框使用與原始檔案卡一致的 `#faf9fd` 淡紫色背景；作答設定、題目內容、解答與解析及提示的實際編輯欄維持白底，讓外層分區與內部輸入狀態清楚區分。
- 同一作答設定列中的作答方式、正確答案與作答格數使用相同的 2.65 rem 高度與 1 rem 外框圓角，不因原生輸入與共用下拉元件不同而出現兩套尺寸或形狀。
- 題目編輯器的「作答方式」與「如何批改」使用全站共用 `AppSelect`，不得以頁面專屬原生 `<select>` 樣式取代設計系統元件。
- 「解答與解析」沒有內容時預設呈現空白文字欄位，包含手動新增題目、小題及解析結果為空的既有草稿，不要求使用者先按「加入內容」；空白欄位只有開始輸入後才更新草稿。作答前提示標題不再顯示「學習者自行展開後才會看到，不會影響判分」的輔助文案。
- 「解答與解析」排在「作答前提示」之前。題目範本不預先建立示範提示；只有使用者主動新增或來源明確提供時才建立。沒有提示時只顯示小型「新增提示」按鈕，有提示時才顯示標題與提示編輯內容。

## 產品結果

使用者拍攝歪斜、旋轉、光線不均或有輕度書頁彎曲的教材後，系統要產生接近掃描 PDF 的平整頁面。使用者可以檢查裁切範圍、頁面方向、影像模式與手寫移除結果，再交由系統辨識題目。系統不得把影像修復產生的像素或 OCR 推測直接當成已確認的題幹、選項或答案。

市場級效果不是指定某個模型或濾鏡。Lerniqa 必須以固定測試集，和 Apple Notes 與 Google ML Kit Document Scanner 的公開掃描能力做相同輸入比較。未通過本文件的幾何、可讀性、內容保留、OCR 與人工修正門檻前，不得宣稱已達到專業掃描 App 的效果。

## 使用者流程

主導覽的「新增題目」進入同一個新增工作區。第一步讓使用者選擇輸入方式：

- 手動建立
- 拍照
- 上傳圖片
- 上傳 PDF
- 貼上文字
- 匯入 Lerniqa 結構化檔案

拍照與圖片先進入掃描校正。PDF 若本身已有文字層與正常頁面幾何，直接保留原頁並擷取文字；只有掃描頁才進入影像校正。系統完成頁面處理後立即保存到登入帳號的個人草稿，再進入逐題校正。手動建立與結構化檔案也使用相同草稿契約。手動建立先選擇範本；拍照、PDF 與格式匯入依小題結構顯示最接近的範本，使用者可在校對時更換。更換範本保留題目內容、分類與來源追溯資料，只重建作答結構。使用者確認內容後可先預覽實際作答介面；只有按下「加入題庫」並完成正式分類，系統才以單一交易建立正式題目。

所有檔案來源入口都支援選擇檔案與剪貼簿貼上。掃描與原稿入口接受圖片及 PDF，格式匯入接受 JSON，題目內容與格式圖片只接受圖片。貼上的內容仍使用同一套格式、大小、權限與上傳驗證；只有文字的剪貼簿內容不得觸發檔案上傳。瀏覽器無法直接授權讀取剪貼簿時，元件應在原操作位置顯示 `Ctrl+V`／`⌘V` 與裝置選檔指引，不得把瀏覽器能力限制顯示為上傳失敗；格式、數量或檔案處理錯誤仍使用錯誤狀態。

新增題目工作台在 900 px 以下改為上下排列。上方導覽列只使用內容所需高度，不得因頁面最小高度而拉高；主內容緊接在導覽列下方。「返回題目總覽」使用指向 `/questions` 的站內連結，不依賴瀏覽器歷史或按鈕事件推算返回位置。

草稿屬於建立帳號，不因帳號角色而改變。學生、家長、家教與不在學的社會人士都能建立草稿；社會人士在草稿階段不需要虛構年級、學期或學校。現有資料表要求批次連到題庫與學習者，因此後端會使用帳號的預設題庫與 self learner(本人學習者)維持批次完整性；這是內部關聯，不是使用者建立草稿前必須做的分類選擇。

草稿更新不得改變來源文件的媒介契約。貼上文字建立的來源可同步更新 `pasted_text`；圖片、PDF 或文件來源持續以 private asset(私人資產)保存原稿，`pasted_text` 必須保持 `NULL`。使用者校正後的題目內容保存於批次候選，不得把草稿 JSON 寫回圖片或 PDF 的來源欄位。

拍照流程必須提供：

- 即時拍攝品質提示，包括失焦、反光、遮擋、頁面未完整入鏡與解析度不足。
- 自動拍攝與手動拍攝。自動拍攝只在頁面邊界穩定且畫面清楚時觸發。
- 自動偵測四角、裁邊、旋轉與透視校正。
- 書本雙頁分割，以及頁面順序調整、重拍、刪除與重新裁切。
- 原色、文件灰階、黑白與自動模式。教材有彩色圖表時，自動模式不得把顏色資訊不可逆地轉成黑白。
- 校正前後預覽。使用者可拖曳四角並切換原圖，不接受結果時可重拍。
- 手寫區域的保留、淡化與移除選項。預設先顯示遮罩，不直接刪除。

基準來源：

- [Google ML Kit Document Scanner](https://developers.google.com/ml-kit/vision/doc-scanner)
- [Google ML Kit Android 整合說明](https://developers.google.com/ml-kit/vision/doc-scanner/android)

Google ML Kit 的文件掃描器是 Android 與 Google Play services 專屬能力。Lerniqa 目前是 Web 產品，因此只把它當成效果與操作基準，不能把 Android SDK 寫成 Web 端既有能力。若未來提供 Android 原生應用程式，可以另行評估直接使用該 SDK。

## 影像處理流程

每個階段都要保存處理版本、演算法版本、參數摘要、輸入與輸出 checksum、執行時間及警告。失敗時保留原始檔與已完成階段，不得產生半套正式題目。

### 原始檔驗證

後端以實際檔案內容確認 MIME type，不信任副檔名或瀏覽器宣告。圖片須限制像素數、解碼後記憶體、色彩通道與頁數；PDF 須限制檔案大小、頁數、物件數、解壓後大小與解析時間。所有原始檔先保存為 private asset，通過惡意檔案掃描後才能處理。

系統保存原始檔，不會用校正圖覆寫。後續重新處理必須從原始檔或明確指定的前一版開始，不能反覆壓縮已處理圖片。

### 拍攝品質檢查

品質檢查至少涵蓋：

- 失焦與動態模糊
- 過曝、反光與大面積全黑區域
- 紙張邊界是否完整入鏡
- 手指、夾具或其他物體是否遮住內容
- 頁面占畫面比例是否足以辨識
- 影像方向與 EXIF orientation

品質門檻要以驗收資料校準，不能把單一固定數字寫死在前端。低品質影像要指出具體問題並要求重拍。系統不得以生成式 AI 補出被遮住或失焦到不存在的字。

### 頁面與角點偵測

第一層使用傳統 computer vision(電腦視覺)偵測邊緣、輪廓、直線與四邊形候選。候選依頁面面積、凸性、角度、相對邊一致性及實際邊緣覆蓋率評分。背景複雜、紙張與桌面顏色接近，或頁面邊界不完整時，再使用文件分割模型產生頁面遮罩。

模型只提供候選。畫面必須顯示最後採用的四角，並允許使用者調整。偵測信心不足時不能靜默裁切。

### 鏡頭與透視校正

若圖片含可信的相機與鏡頭資訊，而且已有對應 lens profile(鏡頭校正設定)，先修正 barrel distortion(桶狀變形)、pincushion distortion(枕狀變形)與暗角。找不到可信設定時不猜鏡頭參數。

平面頁面使用四角計算 homography(單應性轉換)，再以 perspective warp(透視轉換)映射成矩形頁面。OpenCV 的 `getPerspectiveTransform`、`findHomography` 與 `warpPerspective` 可作為基礎實作。輸出尺寸由偵測到的頁面比例、使用者選擇的紙張尺寸與有效來源解析度決定；標示為 300 PPI 不代表可以創造原圖沒有的細節。

技術依據：[OpenCV perspective transform](https://docs.opencv.org/4.10.0/javadoc/org/opencv/core/Core.html)

### 曲面展平

四角透視轉換只能修正平面紙張，不能修正書脊、彎頁與波浪紙張。曲面頁面需要估計 dense displacement field(逐像素位移場)，再重映射整頁。首選候選是 PaddleOCR 文件前處理中的 UVDoc，因為專案已使用 PP-OCRv6，沿用同一套 Paddle 推論環境可減少第二套模型執行環境。

UVDoc 仍須和下列候選在 Lerniqa 教材資料上比較：

- 只做四角透視轉換的 OpenCV 基準線
- PaddleOCR UVDoc
- DocTr 或後續同類文件展平模型，只作研究比較；進入 production 前必須完成授權、模型來源、依賴、安全與維護狀態審查

不能以公開 benchmark 的單一分數直接決定 production 選型。測試資料必須包含繁體中文、注音、數學公式、表格、直式與橫式教材、書脊附近文字、彩色插圖及低對比印刷。

技術依據：

- [PaddleOCR 文件影像前處理](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/doc_preprocessor.html)
- [PaddleOCR UVDoc 文件展平](https://www.paddleocr.ai/main/en/version3.x/module_usage/text_image_unwarping.html)
- [DocTr 官方研究實作](https://github.com/fh2019ustc/DocTr)

### 光線、陰影與紙張背景校正

頁面展平後再估計緩慢變化的背景照明，分離紙張底色、陰影與前景內容。處理順序至少包含白平衡、色偏校正、陰影估計、局部對比與降噪。黑白模式可使用 adaptive threshold(自適應二值化)，但不能把同一組參數套到所有教材。

公式細線、注音符號、表格線、低對比印刷、照片及色塊必須建立保護遮罩。強化結果只要造成筆畫黏合、細線消失、圖片過曝或顏色失真，就應退回較保守的處理版本。原色、灰階與黑白版本可由同一張校正母版產生，不得互相轉存。

### 手指、污漬與手寫處理

手指或污漬移除只能處理位於頁面邊界、空白區，或經人工確認不覆蓋教材內容的區域。遮住印刷內容時，系統要求重拍，不使用生成式填補冒充原文。

手寫去除分成偵測、遮罩、預覽與套用四個階段：

- 模型標出疑似手寫像素，並保存信心值與遮罩。
- 系統擴張遮罩時必須保護印刷文字、表格線、公式與圖片邊界。
- 使用者在原圖疊圖上檢查遮罩，可以擦除或補畫遮罩。
- 套用後同時保留原圖、校正圖、遮罩與去除結果。

手寫移除只改善題目來源頁面，不等於手寫辨識，也不能自動把被移除的手寫內容當成答案。若手寫補充是題目必要條件，使用者必須選擇保留，或在逐題校正階段重新輸入。若移除結果碰到印刷內容，該頁不得自動進入題目發布。

首版不承諾無條件自動去除所有手寫。安全目標是避免刪錯印刷內容；偵測不到的手寫可以由使用者補畫遮罩，無法安全分離時保留原圖並標記待處理。

### 雙頁分割與多頁文件

系統偵測書脊與左右頁面邊界，把雙頁照片拆成兩張來源頁。若書脊附近內容跨頁，或分割信心不足，顯示分割線讓使用者調整。頁碼、來源座標與處理矩陣都以原始影像座標保存，確保題目裁切圖可追溯。

多頁文件支援重排、旋轉、刪除與單頁重拍。重新處理單頁不得讓其他已確認頁面的識別結果失效。

## OCR、版面與題目結構化

掃描處理完成後才執行 OCR。PP-OCRv6 負責文字偵測與辨識；PP-StructureV3 與 General Table Recognition v2 可作為版面、表格及閱讀順序候選。公式不能只依一般 OCR 文字結果發布；無法可靠轉成 canonical TeX 的公式保留為已驗證圖片內容區塊，等待人工校正。

目前的題目結構化由固定本機 Ollama `qwen3.8:27b` 執行。伺服器只連線到沒有帳密的 HTTP loopback。每次分析都傳入校正頁、OCR 全文、各 OCR 行的比例座標與信心值；圖片是抄錄依據，OCR 只供定位。低解析度圖片在送入 vision model 前建立 2,400 × 3,200 範圍內的 Lanczos 放大與銳化副本。國字注音頁另依 OCR 行座標建立放大的灰階文字行圖，讓模型檢查小字筆畫；兩種處理都不覆寫原稿與校正資產。模型回應使用 NDJSON stream(逐行 JSON 串流)，讓長時間生成先建立 HTTP 回應並持續傳回內容；單次呼叫仍受十分鐘整體上限與一 MiB 模型內容上限保護。Undici 的標頭或內容逾時必須回報 `LOCAL_MODEL_TIMEOUT`，不得誤報為模型未啟動。模型依既有八種題目範本輸出 AI 交換格式，不能直接寫入草稿或資料庫。伺服器重新驗證題目、小題、選項、答案方式、表格與 `crop_ref`，再依比例座標建立私人裁切資產並轉成 v2 草稿。拆題時，來源沒有清楚印出的答案就保留空答案並使用 `manual_review`；手寫、圈選及批改符號不能成為答案。拆題完成後可另外產生答案建議，但建議未經使用者確認不得寫入草稿。

中文數字加頓號的章節標題只提供題型、作答方式與計分資訊，不保存為題目內容。章節標題下直接排列的阿拉伯數字項目各自建立為獨立題目，來源題號保存為「章節序號-題號」；OCR 已辨識出獨立題號時，模型輸出 schema 會固定相同題數，只有回答多個相依問題時不可缺少的共用文章、圖片或表格才建立題組。模型誤建題組、重複題號或漏題時，系統會要求模型重新輸出整頁，第二次仍不正確就回報錯誤。「國字注音」與「解釋」章節只允許文字作答，不得虛構選項；國字注音題可使用引號內的純注音目標、引號內國字目標，或放在原作答位置的待確認注音裁切。分類標題混入題幹、三種目標都不存在、注音離開作答位置、含替代字元、空白括號、拉丁字母、日文假名，或同一括號混合國字與注音時，系統會要求模型重新對照原圖；第二次仍不可靠就拒絕建立題目。跨頁共用題幹與複雜版面仍依人工校對與固定資料集驗收，不能只靠題號或字形檢查宣稱完整。

已保存的圖片草稿可從原始私人資產重新分析。只有新結果完成模型輸出、交換格式、草稿契約及資產檢查後，系統才在同一交易替換待確認題目；任何一步失敗都保留原草稿。

草稿清單 API 以帳號權限範圍回傳來源資產的最小預覽資料。圖片草稿在編輯畫面顯示可點擊縮圖，PDF 顯示檔案入口；兩者都透過既有私人資產端點預覽，不新增公開檔案路徑。

分析完成後，系統以 OCR 與題目文字比對現有教材目錄。單元名稱必須完整相符；若同名單元超過一個，再使用文字中的科目、年級、學期與版本縮小範圍。只有唯一候選才預填科目、年級、學期、版本與單元，仍由使用者在「加入題庫」確認。確認後的單元關聯寫入正式題目版本；無法唯一判定時不自動選擇。

技術依據：

- [PaddleOCR PP-StructureV3](https://www.paddleocr.ai/latest/en/version3.x/pipeline_usage/PP-StructureV3.html)
- [PaddleOCR General Table Recognition v2](https://www.paddleocr.ai/v3.0.3/en/version3.x/pipeline_usage/table_recognition_v2.html)

結構化流程輸出帳號草稿，不直接建立已發布題目。每個候選至少包含：

- 來源文件、頁碼、原始座標、校正後座標與裁切圖
- 大題共用內容與依序排列的小題
- 文字、圖片、表格、公式、音訊或頁面裁切內容區塊
- 各小題作答方式、選項、答案候選、解析與信心值
- 科目、年級、學期、版本、冊次、單元與來源分類候選
- 需要人工確認的欄位及原因

系統不得從版面位置猜造標準答案。來源沒有答案，或答案與小題無法唯一對應時，正式草稿答案保持空值。AI 可另外提出附帶信心值與證據的答案建議；無法可靠判斷時不得輸出建議。OCR 或 AI 輸出只能進入 pending candidate(待確認候選)，不能覆寫草稿答案或已發布 revision。

## 題目、子題、圖片與表格契約

每道題目沿用現有 `questions` 與 `question_revisions`。一般單題也建立一筆根 `question_parts`，避免單題與子題走不同保存流程。大題共用內容的 `question_content_blocks.question_part_id` 為空；子題內容連到對應 `question_parts`。巢狀子題使用 `parent_part_id`，順序只由 `position` 決定。

內容區塊沿用現有 `text`、`image`、`audio`、`transcript`、`formula`、`table` 與 `page_crop`。圖片發布前要有替代文字。表格以結構化列與欄校正後再寫入現有 table 契約，不能把整張表只當成 OCR 純文字；無法可靠還原的表格保留為 `page_crop`，不得猜測合併儲存格。

原始頁面、校正頁面、手寫遮罩、去除結果與題目裁切圖是不同 asset。題目內容引用最適合顯示的 asset，來源證據仍可回到原始頁面。

## 答案方式

首版沿用現有四種 `answer_mode`：

- `single_choice`：單選
- `multiple_choice`：複選，正確集合必須完整符合
- `boolean`：是非
- `text`：文字與多欄文字

判分沿用 `automatic`、`manual_review` 與 `ai_assisted_review`。自動判分的單選、複選與是非題必須有屬於同一小題的有效答案鍵；自動判分文字題必須有非空白可接受答案。多欄文字題只允許人工檢視，欄位數必須來自經確認的來源結構，不從答案標點或空白數量推測。

答案校正介面要同時顯示來源裁切圖、小題、選項及答案。答案來源不清楚時只能保存草稿或待檢視，不得為了通過發布限制而改成人工判分或補造答案。

## 結構化匯入格式

豐富題目不能以 CSV 作為唯一正式格式。圖片、表格、公式、巢狀子題、多答案及來源證據使用 versioned JSON package(有版本的 JSON 封裝格式)。格式匯入使用與手動建立共用的題目範本清單，可選擇一種、多種或全部題型。系統依選取結果產生多題 JSON、下載檔與可直接交給外部 AI 的指令，不加入未選題型。每題包含 `templateId`，匯入器會核對實際小題與作答結構，不能只信任名稱。

格式分為兩個邊界。`schemaVersion: 1` 的 AI 交換格式供外部工具產生，不包含帳號、學習者、分類或內部資產識別碼。驗證並補齊圖片後，前端把它轉成既有 `schemaVersion: 2` 草稿。資料庫、草稿 API、預覽與發布流程只接受 v2，不保存未解析的圖片參照。

AI 交換格式可在 `questions` 放入 1 至 100 題。文字、公式與表格沿用草稿內容區塊；圖片使用以下兩種參照：

- `image_ref` 以 `ref` 與替代文字表示一張獨立圖片。使用者從裝置或 Google 雲端硬碟選取對應檔案後，系統上傳為 `question_content` 私人資產。
- `crop_ref` 以 `ref`、`sourceRef`、1 起算頁碼、0 至 1 的比例座標及替代文字表示原稿中的區域。同一份交換格式只能有一個 `sourceRef`。系統先處理原稿，再顯示裁切框與裁切結果供使用者調整。

交換格式不接受 Base64、遠端圖片 URL 或內部 `assetId`。Base64 會放大檔案與 AI token 用量；遠端 URL 會帶入失效、追蹤與伺服器端請求風險；`assetId` 只有在登入帳號完成上傳後才存在。多檔 ZIP 封裝不屬於目前交付範圍，日後加入時須保存 manifest 與每個檔案的 SHA-256，並沿用同一個參照解析器。

草稿 JSON 使用 `schemaVersion: 2`，根層只接受 `schemaVersion`、`sourceTitle` 與 `questions`；匯入器仍接受 v1 並補上穩定題目鍵值。學習者與題庫不屬於草稿檔案，避免匯出後綁死特定帳號資料。每題可保存帳號自訂分類的正式 ID；匯入其他帳號時若無法通過擁有權與科目範圍檢查，必須先移除或重新選擇。題目內容至少要表達：

- 題目與 revision 身分
- 共用內容、小題樹與穩定鍵值
- 內容區塊、顯示位置與資產引用
- 選項、作答方式、判分政策與答案
- 選填的題目來源頁碼與來源題號；手動新增不顯示，掃描頁碼由系統保存
- 每題穩定的 `draftKey`，以及選填的分類欄位與選項 ID
- 題目之間的引用，不接受可執行腳本或遠端資產 URL

匯入器必須先驗證 schema、資產 checksum、引用完整性、數量上限與擁有權，再建立草稿。未知欄位、未知 enum、重複 stable key、跨題引用及缺少資產一律拒絕，不採寬鬆 fallback。正式發布封裝另包含登入帳號可存取的學習者、冪等鍵、草稿批次與目錄分類；後端再次完整驗證，不信任前端草稿。

裝置上傳、拍照、內容圖片、格式圖片配對、原稿上傳與 Google Drive 共用同一個檔案來源元件。系統檔案選擇器是主要入口，而且不得帶 `capture` 屬性，讓平板或手機依本機設定列出裝置儲存空間、Google Drive、iCloud Drive 等文件提供者；「拍照」則使用獨立輸入並指定後鏡頭。這兩個入口不能合併，否則部分行動瀏覽器會直接開啟相機而隱藏檔案與雲端來源。

Google Picker 是選配的網頁 Drive 入口，前端先讀取伺服器公開設定，只有 OAuth client ID、Picker API key 與 Cloud project number 完整時才顯示按鈕。Google Picker 依使用位置限制為 JPG、PNG、WebP、PDF 或 JSON，允許需要的多選情境。後端只向固定的 Google Drive API 主機要求使用者選取的 file ID，先檢查 `capabilities.canDownload`、檔名、大小與 MIME type，再以內容嗅探驗證。服務不保存 Google access token，也不把 Google Drive URL 寫入題目。

圖片資產目前只接受 JPG、PNG 與 WebP；掃描來源另接受 PDF。若解碼環境不能可靠處理 HEIC／HEIF，API 回傳可採取行動的錯誤訊息，要求使用者先由裝置另存為 JPG。不得只更換副檔名，也不得在未驗證像素內容時宣稱完成轉檔。

## 處理架構

拍照與 PDF 處理採 asynchronous job(非同步工作)。Next.js API 只負責授權、保存來源、建立或查詢工作與確認結果；獨立影像 worker 負責解碼、校正、OCR、版面分析與本機模型拆題。上傳成功即建立持久工作並進入草稿畫面，使用者可以離開；重新進入「我的草稿」後，等待 worker 與 worker 執行中的草稿都顯示「處理中」，完成後顯示「可編輯」，失敗時顯示「分析失敗」。worker 只從資料庫與私人資產取得已驗證輸入，不使用前端傳來的檔案路徑、模型名稱或 shell 參數。

工作以 `question_source_analysis_jobs` 保存狀態、設定、可執行時間、租約、嘗試次數、錯誤碼與完成結果，並以 `question_source_analysis_runs` 保存每次嘗試。worker 使用 `FOR UPDATE SKIP LOCKED` 領取工作，執行期間定期延長租約；程序中斷後由租約逾時機制標記該次執行失敗並依上限重試。新題目、頁面資產與完成狀態在同一交易寫入，失敗時保留原始檔與既有候選，不留下部分替換結果。同一批次同時只能有一個有效工作。

worker 啟動時會補登背景工作上線前已完成上傳、仍為 `draft / uploaded` 且從未建立分析工作的圖片或 PDF。補登為冪等操作，不會自動重跑 `failed`、`review`、`confirmed` 或已存在任何分析紀錄的批次。

建議沿用專案現有 PaddleOCR 經驗，但為文件掃描建立獨立、固定版本的 Python 環境，避免手寫辨識與文件版面模型的依賴互相覆寫。所有模型要固定名稱、版本與 checksum，不允許 production worker 啟動時自動下載或替換模型。

產品狀態由來源文件、匯入批次及背景工作共同表達：來源文件使用 `uploaded`、`processing`、`ready`、`failed`；匯入批次使用 `draft`、`recognizing`、`review`、`confirmed`、`failed`、`cancelled`；背景工作使用 `queued`、`retry`、`running`、`completed`、`failed`、`cancelled`。每個狀態轉換由後端驗證。重試使用相同來源 checksum 與處理設定，不重複建立有效工作；只有完整成功的結果可取代尚未發布的候選。

## 權限與資料安全

- 一般帳號只能查看與修改自己建立或匯入的題目；系統題目只允許 system admin 建立或修改。
- 帳號自訂科目、分類欄位與選項只對建立帳號可見；目錄 API、發布驗證與 AI 分類都必須重做擁有權檢查，不能信任前端傳入的 ID。
- AI 分類只傳送題目文字與目前科目的封閉選項清單到固定本機 Ollama loopback。模型回傳的題目、欄位與選項 ID 必須逐一對照伺服器允許清單；本機模型不可用時保留手動分類流程。
- 圖片拆題只傳送縮放後的校正頁、OCR 文字、頁碼與固定規則到同一個 loopback。模型輸出不能攜帶遠端 URL 或內部資產 ID，也不能繞過交換格式與草稿契約。
- 原始教材、頁面與裁切圖都是 private asset。下載權限從題庫、題目與建立者關係反查，storage key 不是授權憑證。
- OCR 與影像模型只接收處理所需的頁面，不接收帳號密碼、作答紀錄或無關學習者資料。
- 外部模型服務預設不使用。若未來需要雲端服務，必須另行核准資料範圍、保存政策、供應商條款與刪除證據。
- 日誌不記錄完整頁面、OCR 全文、答案、私人檔案路徑或可重建教材的 base64。
- 使用者刪除草稿前，介面必須顯示草稿名稱、不可復原後果與取消操作。確認後依正式保存政策解除引用並排程物件刪除；不能只刪資料庫列而留下無主檔案。

## 品質驗收

### 固定測試集

建立經授權、可重複使用的拍攝測試集。每一頁保存原始平面掃描或人工校正頁作為參考，測試情境至少包含：

- 正拍、四個方向的斜拍與不同距離
- 輕度與明顯書頁彎曲、書脊陰影及雙頁書本
- 日光、黃光、局部陰影、反光與不均勻亮度
- 白紙、米色紙、彩色底、照片、圖表與低對比印刷
- 繁體中文、注音、英文、數字、數學公式與直式文字
- 無框表格、有框表格、合併儲存格及圖片選項
- 鉛筆、原子筆、螢光筆、圈選、批改符號及手寫覆蓋印刷內容
- 可安全處理與必須要求重拍的負面樣本

測試集依教材來源與頁面分組後再切分，避免同一本書的相鄰頁同時出現在調整集與驗收集。私人教材與未成年資料不得提交到 Git；repository 只保存取得授權的合成或去識別樣本、manifest 與 checksum。

### 發布門檻

門檻先在技術驗證階段用固定測試集校準，之後寫入受版本管理的驗收設定。不得在每次執行時為了讓測試通過而改門檻。

正式開放前必須同時符合：

- 在「頁面完整入鏡、沒有不可恢復失焦或遮擋」的支援情境中，至少 90% 頁面不需人工調整四角即可得到可用裁切。
- 校正頁面的四角平均誤差不得超過頁面對角線的 1%，且不能裁掉參考頁中的題號、文字、圖片或表格邊界。
- 曲面展平後的文字基線與表格線要比只做透視轉換更接近參考頁；若模型讓結果變差，必須自動採用較保守版本或要求人工選擇。
- 掃描校正後的 OCR character error rate(字元錯誤率)不能比同頁原始照片差；整體相對錯誤率須比原始照片至少降低 20%。公式與表格另行計分，不能用一般文字的高分掩蓋失敗。
- 手寫去除驗收集中，印刷字元、公式、表格線及必要圖片的誤刪數必須為 0。未移除乾淨可以轉人工處理，刪掉教材內容不能接受。
- 同一批支援情境照片分別經 Lerniqa、Apple Notes 與 Google ML Kit 處理後，至少三名不知道結果來源的評估者比較可讀性、幾何平整、陰影與內容保留。Lerniqa 在各核心項目不得顯著劣於兩個市場基準；任何內容遺失直接判定該頁失敗。
- 桌面與 390px 手機寬度都能完成拍照或上傳、調整四角、切換濾鏡、檢查手寫遮罩、逐題校正與保存草稿，不產生水平頁面溢位。
- 中斷、逾時、重送與 worker 重啟不產生重複題目、遺失原始檔或半套發布版本。

盲測只比較同一張原始照片，並保存 App、作業系統、裝置與測試日期。第三方產品更新後，基準結果可能改變；重做重大影像處理版本時必須重新執行盲測。

### 效能門檻

拍攝畫面中的邊界提示與品質警告應維持可互動，不等待伺服器完成整頁處理。完整解析度處理在背景執行，介面持續顯示每頁狀態並允許離開後返回。

技術驗證先在目標本機 CPU、production 等級 CPU 與可用 GPU 上量測每一階段的 p50、p95、尖峰記憶體與模型載入時間，再核准正式時間預算。不能把研究論文或供應商硬體上的推論時間直接當成 Lerniqa 的效能承諾。

## 施工順序

### 技術驗證

先建立固定測試集與基準工具，實測 OpenCV 平面校正、UVDoc 曲面展平、光線校正及手寫遮罩。輸出並排比較頁與量測報告。這一階段不接正式題庫，也不修改持久資料。

### 上傳與處理證據

補齊 private asset、處理 job、頁面版本、轉換矩陣、遮罩與模型身分所需的 schema。完成冪等、取消、重試、失敗回復及物件清理測試。

### 掃描校正介面

完成拍照、圖片與 PDF 上傳，多頁管理、四角調整、濾鏡與手寫遮罩預覽。桌面與手機都要以真實相機照片操作驗證。

### OCR 與逐題校正

把 OCR、版面、表格與題目拆分結果保存為候選。完成大題、子題、圖片、表格、選項、答案及分類校正介面，不直接發布。

### 正式保存與入口開放

以單一交易建立題目、第一版、小題、內容、選項、答案、分類、來源與題庫收錄。完成授權、免費方案額度、版本與稽核驗證後，才恢復主導覽「新增題目」。

## 不在本階段承諾的能力

- 還原被手指、反光、失焦或撕裂完全遮住的文字
- 以生成式 AI 補寫來源中不存在或看不清楚的題目，或未經使用者確認就把推導答案寫入草稿
- 不經人工確認就刪除覆蓋印刷內容的手寫
- 對所有教材、相機與拍攝條件保證相同結果
- 在技術驗證前承諾特定模型就是 production 最終選擇

這些限制不降低專業效果要求。它們用來劃清影像改善與內容捏造的界線；專業掃描流程在無法安全處理時應要求重拍或人工校正。
